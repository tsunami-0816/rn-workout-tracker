## 2. 拐点判定

- **RPS 在 20 并发饱和**：`/plans` 10→20 并发 RPS 增长 56%（74.6→116.4），20→50 反而下降 5.1%（116.4→110.5）；`/workouts` 20→50 下降 12.5%（178.4→156.0）。
- **RT 在饱和后陡增**：50 并发相对 20 并发，`/plans` p95 从 239.2→610.1（**2.55×**），`/workouts` 146.2→458.9（**3.14×**）；p50 分别 2.70× / 2.86×。
- **错误率为 0**：吞吐没有崩，请求在队列里等——这是**资源排队型瓶颈**，不是服务崩溃型瓶颈。
- `perf.json` 里有 5 个采样点，p95 与 RPS 的交叉点在 **20 并发**附近，可作为「单实例健康容量」口径。

## 4. TPS 瓶颈分析（证据 → 定位 → 根因 → 验证 → 建议）

### 4.1 证据链

1. RPS 平台期 + RT 线性上升 + 0 错误 → 系统在**排队**，吞吐被某个共享资源卡住。
2. `/plans` 每请求 SQL 次数约为 `/workouts` 的 1.5 倍（3 次 vs 2 次），同并发下 RPS 低 35%~38%（116 vs 178），p95 高 64%——**瓶颈与「每请求 DB 往返次数」强相关**。
3. 50 并发时 `/plans` p95 610 ms ≈ 20 并发 239 ms × 2.5，接近「连接池排队 × 单查询耗时」的量级叠加。

### 4.2 定位

- 入口：JWT 校验（同步 `jwt.verify`）→ 控制器 → 服务层 Prisma 查询 → 序列化。
- 关键共享资源：
  - **Node 单进程事件循环**：JS 侧 CPU（JWT 解析、DTO 校验、JSON 序列化）串行；50 并发下事件循环排队。
  - **Prisma/PG 连接池**：连接数有限，`/plans` 每请求 3 次查询，50 并发 ≈ 150 SQL/轮，超出连接数即排队。
  - **无缓存**：`/plans` 与 `/workouts` 列表都每次打库（统计接口有 60s 缓存，本轮未压）。

### 4.3 根因（假设 + 可验证方式）

| 假设 | 验证方式 | 预期现象 |
|---|---|---|
| Prisma 连接池饱和 | 50 并发下 `select count(*) from pg_stat_activity where datname='rn_workout'` 观察 active 连接贴顶 | active ≈ connection_limit，其余等锁 |
| 事件循环排队 | 压测同时请求 `/api/health`（不查库）观察 RT 是否也升高 | health p95 明显上升 → 事件循环/接受队列排队 |
| SQL 次数放大 | 打开 Prisma query log 统计单请求 SQL 数 | `/plans` 3 条/请求，`/workouts` 2 条/请求 |

### 4.4 调优建议（按 ROI 排序）

1. **给 `/plans` 加 60s 读缓存（最高 ROI，0.5 天）**：统计接口已有 `invalidateByPrefix` 机制，复用同套即可；计划列表一天最多变一次。预期：`/plans` p95 在 20 并发降到 **<150 ms**，50 并发降到 **<300 ms**，同时把 Q-001 的 `weekDone` 计算从每请求一次聚合查询里摘出来。
2. **Prisma 连接池显式调参 + Node cluster（0.5 天）**：`connection_limit` 由默认值调到 20~30，配合 `pgbouncer`（transaction 模式）或 Node `cluster` 2 实例；单机 16GB 可承载 2 个 Node 实例 + 1 个 PG。
3. **SQL 合并**：`/plans` 的「计划 + 今日 workout + 本周完成数」三查可并为 1 条带 `LEFT JOIN` 的查询，或把 `weekDone` 挪到统计缓存。
4. **索引复核**：`workout_logs(user_id, log_date)` 唯一索引已覆盖高频路径；确认 `set_logs(workout_log_id, exercise_id, set_no)` 复合唯一索引和 `plans(user_id, sort_no)` 索引存在（C04 已建，压测未发现回表热点）。
5. **JWT 校验缓存（低优先）**：`jwt.verify` 是纯 CPU，50 并发下占比有限；如后续上千 QPS 再考虑。

## 5. 交叉复核与降级边界（如实披露）

- **JMeter 未安装**：`where jmeter` 无结果，本机没有 JMeter CLI；按 step08 §8.5.2 的允许路径降级，不伪造 JMeter 报告。
- **第二套客户端复测（urllib，20 并发 5s）**：

| 接口 | httpx@20 RPS | urllib@20 RPS | 偏差 | httpx p95 | urllib p95 |
|---|---|---|---|---|---|
| `/plans` | 116.39 | 93.17 | **-19.9%** | 239.2 ms | 350.9 ms |
| `/workouts` | 178.39 | 121.16 | **-32.1%** | 146.2 ms | 244.1 ms |

- **结论（不吹一致）**：两套客户端在 20 并发下**均为 0 错误**、RT 同量级；RPS 偏差 20%~32% 来自 urllib **无 keep-alive**（每请求新建 TCP + TLS 握手开销），属于测量方法差异，不是服务不稳定。**绝对值以 httpx（连接复用）为准**；若需要 JMeter 口径的精确对照，需安装 JMeter 后用 keep-alive 线程组、同连接数设置复测。
- 因此 C09/C12 的达标判定采用 httpx 数据；urllib 仅作「另一网络栈无错误」的交叉证据。
