## 一、选型对比（3 题）

### Q1. 为什么用 Expo/RN，不用 Flutter 或原生？
- **30 秒版**：约束是没有 Mac、没有 Android 开发者账号、内存 16GB。Flutter 只适合做对照演示，出 Android 包要 SDK，iOS 还要 Mac；原生双端等于两套工程。Expo 能用一份 TS 代码出 APK，我实际用它出了 1.0.0、1.0.1、1.0.2 三个包并在真机装过。Flutter 我做了登录 + 列表两屏做对照，差异表在交付包里。
- **追问 1**：Expo 的托管服务是不是限制了你的原生能力？→ 是。我没用到需要自定义原生模块的能力；如果要做蓝牙/后台定位，我会走 dev client 或裸 RN。
- **追问 2**：RN 的性能你怎么保证？→ 长列表用 FlatList 固定 64 行高 + `getItemLayout` + `windowSize=7`；100 条夹具只在测试时开。真机 FPS 我没采到（诚实边界），只验证了 12 条列表滚动不卡顿、不横向滚动。
- **追问 3**：为什么不用 uni-app/Taro？→ 它们面向 H5/小程序，我要的是能装进 Android 的原生包与覆盖升级链路；那两类由我另外的项目覆盖。
- **答不上来时的诚实说法**：Flutter 我只跑了两个页面，Dart 的状态管理和原生插件没深入用过，不能按"会用 Flutter 开发"来算。

### Q2. 为什么后端用 NestJS + Prisma，不用 Spring Boot + MyBatis？
- **30 秒版**：这个项目的 JD 里 Node 后端是 must，Java 已由其他项目证明。NestJS 的 Guard/Interceptor 和 DTO 校验适合把 JWT+RBAC 做薄；Prisma 的迁移是一等公民，5 张表和两条复合唯一能落到 SQL 里，不用手写 XML。
- **追问 1**：Prisma 的坑是什么？→ 原生 SQL 的日期校验它不管：传 `2026-13-01` 这类非法日历日，正则过了它到 DB 才炸成 500。我加了 UTC 往返的 `assertDate`，补了单测。
- **追问 2**：Prisma 相比 TypeORM 的取舍？→ 类型安全更强、迁移可读；代价是复杂聚合要 `$queryRaw`，我在统计里就是这么做的，参数化、不拼字符串。
- **追问 3**：为什么不用 MySQL？→ 这台机器上 PG 容器起得快，JSON/窗口函数这些以后扩展方便；没有强依赖 MySQL 的 JD 要求。
- **答不上来时的诚实说法**：Spring Boot 版本我是另一个项目在用；NestJS 的微服务/消息队列我还没在生产规模上跑过。

### Q3. 为什么用 EAS 云端打包，不在本地出 APK？
- **30 秒版**：本机没有 Android SDK，16GB 内存也不适合同时跑 Gradle 和 Metro。EAS 出包是现成路径，JD 也把"发布链路"写成 must。cost 是排队时间和额度，我 1.0.2 前失败过两次（Q-011）。
- **追问 1**：失败原因是什么？→ 工程在 git 子目录里，EAS 把仓库根当工程根，子目录又带 Windows 反斜杠，Linux worker 找不到 `package.json`。我把工程复制到仓库外纯 ASCII 目录、`EAS_NO_VCS=1`，632KB 上传后构建成功。
- **追问 2**：云端构建的产物体积你控了吗？→ 1.0.2 是 77,412,373B；1.0.0/1.0.1 约 73.8MB。没有做 ABI split，因为只是自用分发。
- **追问 3**：更新怎么发？→ 改 `release.json`（version/buildNo/apkUrl/notes），APK 放 `10_交付/apk`，后端 `/apk` 静态托管；App 冷启调 `/api/app/version` 比对。
- **答不上来时的诚实说法**：应用商店上架（签名、隐私政策、审核）我没做过；现在只是浏览器下载安装。

## 二、最难的问题（3 题，全部来自真实记录）

### Q4. 统计「本周」一开始算错了，怎么发现的？
- **现象**：5.5 独立 Review 打回，说「本周」实际按滚动 7 天算，周一录的数据会被算进上周。
- **定位**：先看 `stats.service.ts` 的 `$queryRaw`，发现是 `now() - interval '7 days'`；再看单测 `stats.service.spec`，它把 `$queryRaw` 返回值整体 mock，只断言 mock 的 days/volume，SQL 范围根本没被覆盖。
- **根因**：两层：① 需求口径写成「本周」，实现按近 7 天近似；② 测试替身把被测抽象整体替换，真实 SQL 全绿也发现不了。
- **修法**：改成按本地时区周一 00:00 起算；补 L3 集成用例：直插上周五 100kg 记录，断言本周 days=1、totalVolume<100，并与 DB 本周 sum/count 对账，4 周序列的 `series[-2]` 含 100。
- **防回归**：`stats.service.spec` 保留，但「本周范围」只信 L3 直插真实的用例；这条进台账 Q-001，状态 verified。
- **追问 1**：为什么不用数据库时区函数？→ 用了 `date_trunc('week', now() AT TIME ZONE 'Asia/Shanghai')` 这类口径，容器和 Node 都设 TZ=Asia/Shanghai，避免 UTC 偏移。
- **追问 2**：多实例部署时缓存怎么办？→ 现在是进程内 Map，60s。多实例要换 Redis，这条在已知边界 Q-024 里。
- **追问 3**：怎么证明修完没把 4 周柱弄坏？→ 同一条 L3 用例同时断言 4 周序列长度与 `series[-2]` 的值。
- **答不上来时的诚实说法**：本周口径我只覆盖了周一起算，跨年周（ISO 周）没专门写用例。

### Q5. 真机上「训练结束后点取消没反应」，怎么定位的？
- **现象**：用户原话「训练完成后点取消没用」。结束训练后组次卡还显示「已完成 · 点击取消」，点下去页面没反应。
- **定位**：先在 `toggleDone` 里看到命中 `workoutFinished` 直接 `return`；再看 `SetRow`，`disabled` 时把 `onPress` 置空。两条路都把事件吞了，所以既不报错也不提示。
- **根因**：锁定态只在逻辑里判断，没在 UI 上表达；加上静默 return，用户只能判断"坏了"。
- **修法**：`setRowActionLabel(done, locked)` 在锁定态显示「已完成（已锁定）」/「未完成（已锁定）」；`toggleDone` 命中结束态时弹 Toast「本次训练已结束，记录已锁定，不能再改」；步进与删除一起禁用。补 3 条纯函数用例，1.0.2 真机 S11 复验。
- **防回归**：规矩定成「不可用态必须留可见原因」——颜色、文案、Toast 三选一，禁止静默 return。
- **追问 1**：为什么不在结束时就隐藏按钮？→ 隐藏会让用户以为记录丢了；显示锁定态 + 原因更清楚。
- **追问 2**：Toast 会不会被快速连点刷屏？→ `ToastHost` 单例 2.4s 覆盖式显示，后一条替换前一条，不堆叠。
- **追问 3**：后端有没有兜底？→ 有。结束后再写组次返回 40901，探针 `step7_probe.mjs` 覆盖。
- **答不上来时的诚实说法**：我只在华为一台真机上复验，其他机型没测。

### Q6. EAS 构建连续失败，你是怎么查的？
- **现象**：1.0.2 第一次 build `cac63691` ERRORED，日志说找不到 `package.json`。
- **定位**：拉 EAS 日志（`fetch_eas_log.py`），看到 worker 的工作目录是仓库根，而 `eas.json` 里的路径是 `05_代码\frontend`——反斜杠在 Linux 上不是分隔符；同时 EAS 把 git 仓库根当成工程根。
- **根因**：两层：① Windows 路径分隔符；② 工程在 git 子目录里，EAS 的 VCS 上报把根抬到了仓库根。
- **修法**：把工程复制到仓库外 `D:\easbuild\rn-workout`，纯 ASCII 路径，node_modules 用 junction 接过去，`.easignore` 排除无关文件，`EAS_NO_VCS=1` 关掉 VCS 上报；632KB 上传后 build `7428ce1c` FINISHED。
- **防回归**：写进交付包的构建规约：Windows + EAS 一律在仓库外 staging 构建，不在 git 子目录里直接 build。
- **追问 1**：为什么不用 `--local` 本地构建？→ 本机没有 Android SDK，也不适合跑 Gradle。
- **追问 2**：staging 里 node_modules 用 junction 会不会带进构建缓存？→ `.easignore` 排除了缓存目录，上传只有 632KB。
- **追问 3**：失败花了多久？→ 两次失败 + 定位约 57 分钟，第三次成功。
- **答不上来时的诚实说法**：EAS 上游为什么把子目录路径转成反斜杠，我没追到源码级原因，只做了规避。

## 三、再做一次（2 题）

### Q7. 再做一次，架构上你会改什么？
- **30 秒版**：把「统计缓存」和「发码频控」从进程内状态挪到 Redis，从一开始就按多实例设计。现在两处都是 Map，单机演示够用，多副本就失效——这是 Q-024 的根。
- **追问 1**：为什么不是先加单测？→ 单测是底线，不是架构改进。真正会卡住上线的是多实例状态与传输安全。
- **追问 2**：Redis 会带来什么新问题？→ 多一个中间件与网络失败分支；统计缓存要处理击穿，发码频控要处理原子性（INCR + EXPIRE）。
- **追问 3**：还有别的架构改动吗？→ 会把 admin 的只读查询拆到独立读模型/视图，避免和写路径抢连接池；现在 50 并发 p95 610ms 就是连接池与事件循环排队（Q-014）。
- **答不上来时的诚实说法**：Redis 版我只在别的项目用过缓存，没做过发码频控的原子限流。

### Q8. 再做一次，交付流程上你会改什么？
- **30 秒版**：把「链路末端」——EAS 打包、Flutter 对照、真机性能采样——从配套范围提到和 must 同批排期，并在 5B 收口后立刻做一轮真机走查，而不是堆到第 6 步阶段二。
- **追问 1**：为什么？→ 这次 5.5 打回里有 7 条是链路末端没做（D-38~D-44），真机反馈 Q-009/Q-010 也是最后才暴露；越晚发现，返工越贵。
- **追问 2**：真机走查提前会不会打断开发？→ 会占一次安装/复验时间，但比最后三轮安装（1.0.0→1.0.1→1.0.2）便宜。
- **追问 3**：还有什么流程改进？→ 代码冻结后再做关键项审批。这次审批被新提交作废了两次（`cfa5760`→`4b357a5`→`70659c1`）。
- **答不上来时的诚实说法**：并行多项目时怎么保证每轮只读一个项目上下文，我还在摸索。

## 四、细节深挖（4 题）

### Q9. 「一天一练」和组次幂等是怎么保证的？
- **30 秒版**：数据库层兜底。`workout_logs` 上有 `(user_id, log_date)` 复合唯一，重复开练走 upsert/复用同一个 workoutId；`set_logs` 上有 `(workout_log_id, exercise_id, set_no)` 复合唯一，同一组重复提交不会写两条。应用层只做「先查再建」，真正的冲突由 DB 抛，再翻成业务码。
- **追问 1**：并发两个请求同时开练会怎样？→ 唯一约束让其中一个失败，服务捕获后按「已存在」返回同一个 workout；我用 5/10 并发探针验过，没出现两条同日记录。
- **追问 2**：组次重复提交返回什么？→ 幂等成功（不新增行），不是 409；因为用户重试是正常行为。
- **追问 3**：日期用哪一天？→ `log_date` 按 `Asia/Shanghai` 的本地日，容器与 Node 都设了 TZ。
- **答不上来时的诚实说法**：跨时区用户没做，演示环境固定 Asia/Shanghai。

### Q10. JWT + RBAC 的校验链与越权拦截？
- **30 秒版**：`JwtAuthGuard` 解 token 挂 user 到 request，`RolesGuard` 读 `@Roles('admin')` 元数据比对角色；admin 控制器整组挂 `@Roles('admin')`。普通号调 `/api/admin/*` 返回 403 / 40301。前端也藏入口，但只当体验，不当安全边界。
- **追问 1**：token 失效怎么处理？→ 前端 `apiClient` 遇 401 清 SecureStore/AsyncStorage 回登录页；后端返回 40101。
- **追问 2**：role 能被前端改吗？→ role 存在服务端 user 表，登录时签发进 token；改本地存储只会 403。
- **追问 3**：为什么不用 CASL/权限矩阵库？→ 只有 user/admin 两角色，手写 Guard 更薄；角色多了再上策略库。
- **答不上来时的诚实说法**：演示验证码是全局共享的，知道码就能登 admin——这是鉴权设计缺口（Q-018），不是 RBAC 本身的问题。

### Q11. 组次的乐观回填与失败回滚怎么做的？
- **现象补充**：先在本地改 state 立即渲染，再发请求；失败时该行标红、保留用户填的数值、给重试按钮；成功后以服务端返回为准。
- **追问 1**：连点「+」会不会发多个请求？→ 步进只改本地；勾「完成」才提交，提交中有 pending 锁，重复点走同一行状态。
- **追问 2**：结束后再提交呢？→ 后端 40901，前端锁定态本来就禁用入口，双保险。
- **追问 3**：断网时表现如何？→ 设计是红行 + 重试 + 数值不丢；**但这条没在真机上走通验证**，第 9 步验收时用户没回传，台账记 Q-025 deferred。这是我要补的第一项。
- **答不上来时的诚实说法**：断网回滚只有代码路径和设计说明，没有真机截图/录屏。

### Q12. 版本发布与回滚链路？
- **30 秒版**：单一版本源 `release.json`（version/buildNo/apkUrl/notes），后端 `/api/app/version` 读它，`/apk` 静态托管 APK；App 冷启比对本地版本，落后就弹更新。回滚就是把 `release.json` 改回上一版并保留旧 APK，App 立刻不弹；数据回滚用 `.sql` 备份恢复到 `pg_data` 卷。
- **追问 1**：release.json 有两份副本怎么办？→ 根目录与 `05_代码/` 各一份，靠约定同步；这是 R2 复审提的 P3，建议改成生成物，还没做。
- **追问 2**：APK 完整性怎么保证？→ 文档记 SHA256（340A0063…B7C7），下载后可比对；生产应做签名校验，现在没有。
- **追问 3**：版本接口性能？→ 20 并发 p95 107ms，第 9 步复测 p95 30ms，目标 ≤200ms。
- **答不上来时的诚实说法**：没有灰度/分批发布，也没有强制更新策略；现在只是"发现新版本→用户选择下载"。
